The Big Picture

StockForge is not a toy. It is a deliberate, day-by-day build of a production-grade stock trading platform — the same kind of system Zerodha or Groww run — that will later evolve into HFT (high-frequency trading) architecture. Each "day" is a ~30-minute unit that builds a real piece of the platform and teaches the engineering behind it.

Our guiding rules (from the Master Prompt)

  • Teach before automating: understand WHAT / WHY / HOW before writing code.
  • One service = one folder = one repo.
  • Contract-first: pin interfaces before code.
  • Two devices, Git is the source of truth.
  • Observe everything: health checks, logs, correlation IDs from day one.
  • Hypothesis before every change: guess → change → measure → conclude.

Day 1 / 1.5 — Architecture Proposal, then APPROVAL

What: wrote the full Phase 0 architecture (9 services, repo layout, stack, roadmap, 2 ADRs) and — crucially — waited for your approval before writing any code.

The concept: an ADR (Architecture Decision Record)

An ADR is a short document that records why a decision was made, not just what was decided. Two ADRs exist:

  • ADR 0001 — GitHub org + repo layout (one service = one folder = one repo).
  • ADR 0002 — technology stack (later amended: Spring Boot 3.x → 4.1.0).
Production thinking: big systems fail when the reason behind a choice is lost. If you can't answer "why PostgreSQL and not MySQL?" from a document, the next engineer will re-litigate it — or worse, change it based on a guess.

Day 2 — GitHub, Git Workflow, Two Devices

What: created org Stock-Forge, pushed the context repo, and practiced the full git round-trip (branch → commit → push → merge).

The concept: Git as the single source of truth

you (device A) ──commit──▶ local repo ──push──▶ GitHub ──pull──▶ device B change → `git add` (stage) → `git commit` (snapshot) → `git push` (upload) → `git pull` (download)

Key commands we rely on every day:

  • git pull — always FIRST, to sync before work (never start stale).
  • git add -A; git commit -m "message" — stage + snapshot.
  • git push -u origin main — upload + remember the upstream.
  • git status -sb — is the tree clean and is it in sync with origin?
Lesson we hit immediately: on PowerShell, git writes to stderr, which shows as red "git :" text — that is NOT an error. Always verify with git status -sb. This is a tiny taste of why "check the actual state, don't trust the colors."

Day 3 — Contracts: pin the interfaces before the code

What: wrote openapi.yaml (10 paths, 14 schemas, JWT bearer auth) and 7 Kafka event contracts (OrderCreated, OrderExecuted, …).

The concept: contract-first

If five services each assume a slightly different shape for an "order", the system breaks silently. So we write the interface first — the exact request/response JSON — and every service later must satisfy that contract. Version it; never break it.

We use the auth contract constantly — Day 6 was scoped against it: register → 201 / 400 / 409, login → 200 / 401.

Bug we hit: the first openapi.yaml was wrapped in a Markdown fence (```yaml … ```). A .yaml file must be pure YAML — validation failed. Lesson: specs are machine-parsed, so they must be exactly the format the tool expects.

Day 4 — The Web UI: Vite + React 19 + TypeScript

What: scaffolded stockforge-web — a dark-themed trading UI shell with a login placeholder and dashboard status cards ("API not connected yet").

The concepts

  • Vite = the dev server + build tool. Fast (native ESM), ships a starter with React 19 + TypeScript + oxlint (linter) preconfigured.
  • React = UI from components. App.tsx is the root; main.tsx mounts React into the <div id="root"> in index.html.
  • TypeScript = JavaScript with types — the compiler catches mistakes at build time.
npm create vite@latest . -- --template react-ts npm run dev → http://localhost:5173 (dev server) npm run lint → oxlint checks npm run build → tsc -b && vite build (production bundle)
Production thinking: in a real trading platform the UI is a consumer. Speed and correctness live in the backend (matching, risk, auth). The web repo owns its own life — dev, build, lint — and later consumes the OpenAPI contract. Never confuse "the pretty screen" with "the platform".

Day 5 — The API Gateway: Spring Boot, health, logging, correlation IDs

What: scaffolded stockforge-api with: GET /api/health, structured logging, and a correlation-ID filter.

Concept 1 — What a Spring Boot app actually is

Spring Boot runs a normal Java web server (Tomcat) from one small class:

@SpringBootApplication
public class StockforgeApiApplication {
    public static void main(String[] args) { SpringApplication.run(...); }
}

One annotation = "scan for my beans, wire everything, start the server". A Controller maps URLs to methods:

@RestController
public class HealthController {
    @GetMapping("/api/health")
    public Map<String,String> health() { return Map.of("status", "UP"); }
}

Concept 2 — Health endpoints (why a machine cares)

Load balancers and orchestrators call /api/health to decide whether this instance is useful. "UP" → keep sending traffic. Anything else → pull it out and replace it. That's how systems self-heal without humans. (In real HFT this pattern is different — heartbeats, not polls — and we studied that as a bonus topic; see the Learning Log.)

Concept 3 — Structured logging + correlation IDs

Normal logs are free text ("user logged in") — impossible to query. We log key=value lines:

2026-08-08 00:30:19 INFO c.s.auth.StockforgeAuthApplication [correlationId=] Started ...

A correlation ID is a UUID stamped on every request (read from the X-Correlation-Id header, or generated). Every log line from that request carries the same ID, so you can trace one user's action across every service. Real platforms call this distributed tracing — the ancestor of the latency tracing HFT needs.

This is observability-from-day-one: health for machines, correlation IDs for humans, structured logs for tools. You cannot bolt observability on after the fact.

Day 6 — Auth: register/login with bcrypt + JWT

What: built stockforge-auth — the security foundation. POST /api/auth/register and POST /api/auth/login with bcrypt password hashing and signed JWTs. This is the highest-risk area of any trading platform.

How a login actually works (the whole story)

1. register alice@example.com + "secret123" → bcrypt-hash the password → store {id, email, hash, [USER]} 2. login alice@example.com + "secret123" → hash what was typed → compare with stored hash → MATCH? → yes: sign a JWT (header.payload.signature) → return {accessToken, user} → no : return 401 "invalid credentials" (same for unknown email!) 3. later requests → "Authorization: Bearer <JWT>" → any service verifies the signature → trusts who you are (Day 7)

Concept — bcrypt (why we never store passwords)

Hashing is a one-way function: you can't turn the output back into the input. bcrypt is deliberately slow and salted (adds random data), so even a leaked database can't be cracked quickly. Storing the plaintext or even an unsalted hash would be a catastrophe in production.

Concept — JWT (the signed ID card)

A JWT is three base64url parts separated by dots:

eyJhbGciOiJIUzI1NiJ9        ← header: "I was signed with HS256"
.eyJzdWIiOiJhbGljZUBleGFt...  ← payload: subject = email, issued-at, expiry
.xxxxxxxx(signature)           ← proof: HMAC(header.payload, secret)

The signature is the magic: only a server that knows the secret can produce it, so anyone can verify it. That means any service sharing the secret can trust the token with no database lookup per request. Tamper with one character → verification fails.

Design choice worth remembering: we return the same 401 for "unknown email" and "wrong password". Why? Otherwise an attacker can probe which emails exist (account enumeration). Same-oracle responses are standard practice in real auth systems.

Code Walkthrough — the key files of stockforge-auth

User.java — the data shape

public record User(UUID id, String email, String passwordHash, Set<String> roles) {
    public static User create(String email, String hash) {
        return new User(UUID.randomUUID(), email, hash, Set.of("USER"));
    }
}

A record is a compact immutable class (Java 16+): the constructor, getters (id(), email()…), equals/hashCode are auto-generated. create() is a factory that always assigns a fresh UUID and the default USER role.

UserStore.java — in-memory storage (the DB comes later)

@Repository
public class UserStore {
    private final Map<String, User> byEmail = new ConcurrentHashMap<>();

    public User save(User u)          { return byEmail.putIfAbsent(u.email(), u); }
    public Optional<User> findByEmail(String email) { return Optional.ofNullable(byEmail.get(email)); }
    public boolean exists(String email){ return byEmail.containsKey(email); }
}

ConcurrentHashMap.putIfAbsent makes register thread-safe and atomic: two simultaneous registers for the same email → exactly one wins, the other returns the existing user (which our service turns into a 409). This is a mini version of what a database's unique index does.

JwtService.java — sign and verify

public String generateToken(String subject) {
    return Jwts.builder().subject(subject)
        .issuedAt(new Date()).expiration(new Date(System.currentTimeMillis() + expirationMs))
        .signWith(key).compact();
}
public String parseSubject(String token) {
    return Jwts.parser().verifyWith(key).build()
        .parseSignedClaims(token).getPayload().getSubject();
}

The key is derived from the configured secret with Keys.hmacShaKeyFor(...). Every token carries sub = email and an expiry. parseSubject throws on an invalid, expired, or tampered token — which Day 7's filter will convert into a 401.

AuthService.java — the business rules

public UserResponse register(RegisterRequest request) {
    if (userStore.exists(request.email())) throw 409;
    String hash = passwordEncoder.encode(request.password());   // bcrypt
    return UserResponse.from(userStore.save(User.create(request.email(), hash)));
}
public LoginResponse login(LoginRequest request) {
    return userStore.findByEmail(request.email())
        .filter(user -> passwordEncoder.matches(request.password(), user.passwordHash()))
        .map(user -> new LoginResponse(jwtService.generateToken(user.email()), UserResponse.from(user)))
        .orElseThrow(() -> 401 "invalid credentials");
}

Note the .filter(...).map(...).orElseThrow(...) chain: if the email is missing OR the password doesn't match, we fall through to the same 401. One code path, one response — no probing.

SecurityConfig.java — the front door

http
    .csrf(csrf -> csrf.disable())                          // stateless API, no cookies
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/error").permitAll()             // ← fixes 403 masking
        .requestMatchers("/api/auth/register", "/api/auth/login").permitAll()
        .requestMatchers("/actuator/health").permitAll()
        .anyRequest().authenticated())                     // everything else needs auth (Day 7)
    .httpBasic(basic -> basic.disable())
    .formLogin(form -> form.disable());

Stateless + no CSRF + no login page = a pure JSON API. Only register/login/health are public; Day 7 adds the JWT filter that unlocks anyRequest. The /error rule is a real-world lesson: without it, every error (400/404) got re-secured as 403.

The 403 mystery (deep dive): manual tests reported 403 on register. We chased a Spring Security 7 "broken matcher" theory, added a factory bean, saw no change — then the server log revealed the truth: the request reached the controller, but the JSON body had arrived as {email:...} (first quote stripped by PowerShell→curl). The parse error then forwarded to /error, which was secured → 403. Fix: (1) send bodies from files with --data-binary "@file", (2) permitAll("/error"). Lesson: when an API seems to reject everything, read the actual request bytes and server logs before blaming the framework.

Two operational gotchas recorded here

1. PowerShell blocks npm: running npm install in PowerShell fails with "running scripts is disabled" (it tries to load npm.ps1). Fix: use npm.cmd (bypasses the script), run from cmd.exe, or set Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once (admin) to allow it permanently.
2. /actuator/health is active on BOTH services by default: stockforge-api and stockforge-auth include spring-boot-starter-actuator, and health is the one endpoint Actuator exposes over HTTP out of the box (no config needed). Auth's SecurityConfig explicitly permits it, which is why it returns 200 instead of 403. It is the built-in, machine-readable health check; /api/health is the custom one we wrote in the API.
