Key Findings (take-aways, 2026-08-10)

  • GC is not bad — the problem is uncontrolled allocation and GC behavior causing unpredictable latency and tail-latency spikes (a 40 µs order randomly becomes 3,000 µs). Modern collectors (G1, ZGC, Shenandoah) do most work concurrently.
  • JFR = the JVM's black-box recorder. Records GC, allocation, CPU, threads, lock contention, JIT, safepoints, I/O. It does NOT fix anything — it tells you where to look: record → observe → find bottleneck → change → re-test → compare.
  • Lock contention = threads waiting for a shared lock. One thread waiting 1 ms on a 50 µs order path ≈ 1,050 µs total → jitter at p99/p99.9. Mindset: "threads waiting for shared resources create unpredictable latency" — not "locks are slow".
  • Reduce contention: shrink the critical section (risk/fee/logging OUTSIDE the lock), shard state, single-writer, message passing, atomics, lock-free structures, less shared mutable state.
  • Spring Boot does NOT manage GC/threads/JIT/locks — the JVM does. Spring Boot = the control plane (REST, admin, config, monitoring, reporting); the hot trading path should not drag Boot/DB/Kafka along.
  • Core Trading Stack decision (ADR 0003, PROPOSED): first core-trading implementation in plain Java (market data → trading engine → strategy → risk → OMS → exchange gateway) to deeply learn JVM performance engineering. NOT a claim Java > C++ — a C++ equivalent is a later comparison target (latency, GC vs manual memory, CPU, locking, networking, p99.99).
  • Next practical step: JFR practical lab — small plain-Java app, controlled allocation/contention problem, record with JFR, inspect GC/CPU/lock behavior.

The Problem HFT Cares About

Normal order processing is ~40–50 µs. Occasionally an order takes milliseconds. The average looks fine. p99 / p99.9 does not.

Order 140 µs
Order 242 µs
Order 341 µs
Order 43,000 µs
Order 550 µs
The whole field in one chart: one latency spike among thousands of normal orders is a tail-latency problem. HFT performance engineering is about finding and removing the spikes, not about average speed.

Three suspects cause most spikes: GC (memory), lock contention (concurrency), and everything else that JFR can see (CPU, threads, JIT, I/O).

1. Garbage Collection (GC)

What it is

A JVM mechanism that finds objects no longer reachable and reclaims their heap memory.

app creates objects → objects occupy heap → objects become unreachable → garbage accumulates → GC reclaims it → memory free again

Why HFT cares

High allocation rate → heap pressure → GC activity → pauses / CPU / memory pressure → latency spike.

GC is NOT bad. The problem is uncontrolled allocation and GC behavior causing unpredictable latency and tail-latency spikes. Modern collectors (G1, ZGC, Shenandoah) do most of their work concurrently — GC does not mean "everything stops."

Questions to ask when investigating

  • How much are we allocating? What is the allocation rate?
  • How frequently is GC occurring?
  • Which GC is being used?
  • How long are pauses?
  • Is GC consuming significant CPU?
  • What happens to p99 / p99.9 latency?

2. JFR — Java Flight Recorder

JFR = the JVM's black-box recorder. A JVM-level recording tool that captures what happens inside the JVM while a latency problem occurs.

latency problem → start JFR recording → reproduce problem → stop → inspect events → find bottleneck → change code/config/architecture → re-test → compare latency

What JFR can see

GC activity · object allocation · CPU usage · thread activity · lock contention · exceptions · safepoints · JIT compilation · class loading · I/O · JVM pauses.

JFR does not fix anything. It tells you where to look. Example: p99 spikes → JFR → "lock contention" → trading thread waiting → identify the lock → find why it's held too long → optimize.

3. Locks & Lock Contention

What a lock is

A synchronization mechanism that gives one thread exclusive access to a critical section.

synchronized (account) {
    account.balance -= orderValue;
}

Why we need them

Two threads updating the same balance without a lock = race condition. With a lock, one waits while the other works.

Lock contention

Multiple threads want the same lock; some must wait because another thread owns it.

Thread 1 → 🔒 PROCESSING normal = 50 µs Thread 2 → ⏳ WAITING lock wait = 1,000 µs Thread 3 → ⏳ WAITING total ≈ 1,050 µs Thread 4 → ⏳ WAITING
Don't think "locks are slow." Think "threads waiting for shared resources create unpredictable latency." That's what destroys p99/p99.9.

4. Reducing Lock Contention

Shrink the critical section (the big win)

Bad — everything inside the lock

LOCK risk calculation fee calculation response creation logging update state UNLOCK

Better — only the state change

risk calculation fee calculation response preparation LOCK update state UNLOCK

6. Spring Boot vs the Hot Path

Spring Boot does NOT manage GC, threads, JIT, or locks — the JVM does. Spring Boot is a framework that makes services easy to build (REST, DI, config, DB, security, metrics).

Application ↓ Spring Boot (framework — control plane) ↓ Java / JVM (heap, GC, threads, JIT, locks — this is the perf engine) ↓ Operating System → Hardware

The architecture decision this drives

Control plane on Spring Boot: REST APIs, admin, configuration, monitoring, reporting. Hot path in plain Java: market data, matching, strategy, risk, OMS, exchange gateway — no Boot/DB/Kafka dragged along.

7. Core Trading Stack Decision (ADR 0003 — PROPOSED)

Market Data ↓ Java Trading Engine ↓ Strategy → Risk → Order Management → Exchange Gateway
Why Java first? The learning objective is JVM performance engineering: GC → JFR → JIT → threads → locks → lock-free programming → CPU/memory → latency optimization. We are not concluding Java is universally the best HFT language.

Later: an equivalent C++ implementation to compare — latency, GC vs manual memory management, CPU usage, memory behavior, locking/concurrency, networking, p99/p99.9/p99.99.

8. Investigate-a-Latency-Spike Checklist

  1. Confirm the spike with a latency histogram (p50/p95/p99/p99.9).
  2. Record with JFR (black-box recorder — no blind guessing).
  3. Check GC: allocation rate, GC frequency, pause length, GC CPU.
  4. Check locks: which thread waited, on which lock, for how long.
  5. Check CPU hotspots, JIT, safepoints, I/O.
  6. Shrink the critical section / shard / atomics / message-passing.
  7. Re-test, re-record, compare p99/p99.9. Every change = baseline → hypothesis → measure → conclude.
